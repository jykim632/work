# Diagnosis — 문제 진단

이 문서는 [SKILL.md](SKILL.md)의 한글 번역본입니다. 스킬 실행 지침의 기준은 영문 원문입니다.

**설명:** 사용자가 제기한 코드, UI, 문서, 설정 문제를 진단합니다. 범위를 정하고 가능한 경우 증상을 재현하여, 프로젝트 소스, 설정, 테스트를 변경하지 않고 해결책을 제안합니다.

보고된 문제가 실제 결함인지 판단하고, 원인과 영향을 조사하여 해결책을 제안합니다.

언어, 도구, Git 작업 방식, 코딩 규칙, 승인에 관한 프로젝트 지침과 기존 사용자 선호를 따릅니다.

## 범위 확정

- 사용자 요청, 앞선 대화, 제공된 경로, 로그 등의 근거에서 조사 대상을 파악합니다.
- 대상을 특정할 수 없거나, 여러 해석에 따라 조사 방향이 달라진다면 조사 전에 사용자에게 범위를 확인합니다. 원인을 모른다는 이유만으로 추가 설명을 요구하지 않습니다.
- 시작 범위를 짧게 알립니다. 관련 구현, 문서, 호출부, 기존 테스트를 살펴보고, 필요한 경우 직접 연결된 호출과 데이터 흐름을 추적합니다.
- 근거에 따라 기존 범위를 벗어난 별도 기능이나 시스템으로 조사를 확대해야 한다면, 이미 허용된 경우를 제외하고 이유를 설명한 뒤 확대 여부를 확인합니다.

## 기대 동작과 검증 방법 결정

- 사용자 설명, 요구사항, 기존 동작 계약, 디자인 참고 자료, 신뢰할 수 있는 공식 자료에서 기대 동작을 정합니다. 현재 코드, 문서, 테스트가 맞다고 전제하지 않습니다.
- 적용할 기준 없이 시각적 취향을 결함으로 판단하지 않습니다.
- 검증 방법을 선택하기 전에 관련 코드, 기존 테스트의 검증 범위, 실제 실행 환경을 확인합니다.

UI 문제는 필요한 근거에 따라 검증 방법을 선택합니다.

| 필요한 근거 | 우선 선택할 방법 |
| --- | --- |
| 입력, 상태 변화, 이벤트 처리, 결과 DOM 내용으로 판단할 수 있음 | 기존 Testing Library 테스트 |
| 실제 배치, 잘림, 겹침, 스크롤, 브라우저에 따른 상호작용을 관찰해야 함 | Playwright |
| 브라우저 동작과 컴포넌트 동작에 각각 별도의 근거가 필요함 | 목적을 구분하여 둘 다 사용 |

- 실제 실행 환경을 고려합니다. Testing Library는 레이아웃을 계산하지 않는 jsdom에서 흔히 실행되지만, 브라우저에서도 실행할 수 있습니다.
- 코드와 기존 테스트를 살펴본 뒤 위 선택 기준을 적용합니다. 그 후에도 보고된 증상이 브라우저 동작에서 비롯되는지 컴포넌트 로직에서 비롯되는지 구분할 수 없다면, 브라우저에서 증상을 먼저 관찰합니다.
- 아직 해결되지 않은 질문에 답할 수 있을 때만 컴포넌트 또는 브라우저 검증을 추가합니다. 두 도구를 기본으로 모두 사용하거나, 구체적인 이유 없이 동등한 확인을 반복하지 않습니다.
- 프로젝트의 기존 도구를 우선 사용합니다. 선택한 도구나 실행에 필요한 조건이 갖춰져 있지 않다면 한계를 설명합니다. 다른 방법으로 필요한 근거를 확보할 수 있을 때만 사용 가능한 대안을 활용합니다.
- 실행 전에 대상, 선택한 방법, 선택 이유, 추가 검증이 필요한 조건을 짧게 알립니다.

## 조사와 재현

- 가능한 경우 보고된 조건과 조작을 따라 증상을 재현합니다.
- 기존 테스트를 실행하기 전에 보고된 조건을 실제로 검증하는지 확인합니다. 다른 상황을 다루는 테스트가 통과했다는 사실은 참고 근거이며, 보고된 문제를 재현한 것은 아닙니다.
- 진단 단계에서 허용된 범위 안에서 보고된 조건을 실행할 수 없다면, 증상을 재현하지 못했다고 밝히고 확보할 수 있는 조사 근거로 분석을 이어갑니다.
- UI 재현에서는 해당 페이지, 화면 크기, 애플리케이션 상태를 사용합니다. 화면 모습이나 브라우저 상호작용에 관한 문제라면 실제 렌더링 결과를 확인합니다.
- 컴포넌트 테스트가 통과했다는 사실만으로 실제 브라우저 UI가 올바르다고 판단하지 않습니다.
- 실행 환경, 인증, 네트워크, 도구 문제로 인한 실패와 보고된 애플리케이션 결함을 구분합니다.
- 가능한 원인을 확보한 근거와 대조합니다. 직접 관찰한 동작, 코드 조사로 뒷받침되는 결론, 검증되지 않은 가설을 구분합니다.
- 문서나 설정 문제는 설명, 예제, 설정값을 의도한 동작 및 신뢰할 수 있는 공식 자료와 비교합니다. 근거가 충돌하면 조사하고 남은 불확실성을 밝힙니다.
- 확정한 범위 안에서 영향을 받는 작업 흐름과 제안한 수정의 예상 부작용을 파악합니다.
- 확보한 근거로 조사 대상에 대한 답과 실행 가능한 권고를 제시할 수 있으면 조사를 종료합니다. 추가 진행에 확보할 수 없는 근거나 허용 범위 밖의 작업이 필요하다면, 해당 한계와 다음에 수행할 유용한 확인을 보고합니다. 가능한 모든 가설을 소진하기 위해 조사를 계속하지 않습니다.

## 진단 단계의 경계

- 프로젝트 소스, 설정, 의존성, 테스트 파일, 비교 기준 스냅샷을 추가하거나 수정하지 않습니다. 자동 수정이나 스냅샷 갱신을 실행하지 않습니다.
- 실제 데이터와 외부 상태를 변경하지 않는 확인 방법을 사용합니다.
- 실행 과정에서 생성되는 로그, 보고서, 캐시, 스크린샷, 트레이스는 프로젝트에서 정한 임시 산출물 위치나 임시 디렉터리에 저장할 수 있습니다. 이를 프로젝트 변경 사항이 아닌 조사 산출물로 취급합니다.
- 근거로 유용한 경우에만 산출물을 수집하고 프로젝트 규칙을 따릅니다. 비밀 정보나 개인 데이터는 수집하지 않습니다.
- 검증을 위해 누락된 의존성을 자동으로 설치하거나 프로젝트 실행 환경을 변경하지 않습니다.

## 결과 보고

- 결함이 확인되었는지와 증상이 재현되었는지를 밝힙니다.
- 원인이 확인되었다면 원인을 설명하고, 뒷받침하는 근거, 영향을 받는 작업 흐름, 우선순위에 따른 권장 해결책을 제시합니다.
- 실제 사용한 환경과 수행한 확인, 중요한 한계, 검증하지 못한 경로를 보고합니다.
- 해결되지 않았다면 부족한 근거와 다음에 수행할 유용한 확인을 밝힙니다. 코드 조사만 수행한 결과를 브라우저 재현에 성공한 것처럼 보고하지 않습니다.

사용자가 수정을 명시적으로 요청하면 별도의 수정 단계로 전환합니다. 기존 조사 결과를 활용하며, 사용자에게 맥락을 반복하거나 다른 명령을 호출하도록 요구하지 않습니다.
